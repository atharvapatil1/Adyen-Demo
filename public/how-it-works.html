Sessions flow with Drop-in

One API call from your server, everything else is handled by Drop-in in the browser.

  1. Shopper clicks checkout. The browser sends the cart (item ids + quantities) to POST /api/sessions.
  2. Server → Adyen POST /sessions with the API key: merchantAccount, amount (calculated server-side), reference, returnUrl, countryCode, lineItems, and optionally shopperReference for tokenisation.
  3. Adyen returns id + sessionData. The server passes only these to the browser.
  4. Browser creates AdyenCheckout({ session, clientKey, environment }) and mounts new Dropin(checkout). Drop-in fetches the payment methods enabled for this country/currency/amount.
  5. Shopper pays. Card data is encrypted in Adyen-hosted fields (PCI SAQ A). Drop-in calls Adyen directly and handles 3DS2, QR codes and redirects.
  6. Redirect methods return the shopper to returnUrl?sessionId=…&redirectResult=…; the page calls checkout.submitDetails().
  7. onPaymentCompleted / onPaymentFailed give the result for the shopper's UI.
  8. Adyen sends an AUTHORISATION webhook to the server. Verify its HMAC, deduplicate, respond 2xx, and update the order. This is the source of truth for fulfilment.

Sessions vs Advanced flow

Sessions (this demo)
One server endpoint (/sessions). Fastest to build; Adyen manages the payment lifecycle from the client.
Advanced
Three endpoints (/paymentMethods, /payments, /payments/details). Full control, e.g. to change the amount or add data right before /payments, or run your own logic between steps.
